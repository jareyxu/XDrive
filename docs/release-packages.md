# 可扩展发布包与旧更新器迁移

本协议从 v1.3.7 开始启用。已经安装在 VPS 上的 v1.3.6 仍使用原有更新器，需完成升级后才能使用新协议。

## 完整发布包

新安装、手动升级和新版网页更新器使用：

```text
xdrive-vVERSION-linux-amd64-package.tar.gz
xdrive-vVERSION-linux-arm64-package.tar.gz
```

完整包的文件数量由发布清单决定，不要求恰好五个文件。允许在应用安装目录中添加、替换和移除任意普通资源文件，包括嵌套目录中的资源和可执行文件。四个启动文件 `xdrive`、`install.sh`、`upgrade.sh`、`uninstall.sh` 必须存在；`RELEASE.txt` 保存版本、平台、许可证和清单。

新增发布资源放在项目的 `release/files/` 目录中，CI 和本地打包默认自动收集该目录。也可以通过 `scripts/package-release.sh VERSION --files-dir DIRECTORY` 指定其他资源目录。目录内容相对于应用安装根目录组织；不能覆盖打包器提供的启动文件、版本元数据或许可证。打包器只取这个明确的资源目录，不遍历整个项目，因此不会带入本地需求文档、测试数据或密钥。

`RELEASE.txt` 的开头包含 `packageFormat=1`、`version`、`commit`、`os`、`architecture`，空行后的许可证正文末尾附加：

```text
--BEGIN XDRIVE PACKAGE MANIFEST--
{"format":1,"files":[{"path":"assets/icon.svg","size":123,"sha256":"...","mode":420}]}
--END XDRIVE PACKAGE MANIFEST--
```

示例省略了必须声明的启动文件。`files` 列出除 `RELEASE.txt` 本身外的全部归档文件。`mode` 是十进制权限值，允许 420（0644）或 493（0755）。清单、元数据及每个成员都受到整个归档的 SHA-256 校验保护；清单不能给自己声明哈希。

路径是应用资源路径，最长 240 字节，各组件允许 ASCII 字母、数字、下划线、点和连字符。禁止绝对路径、`.`、`..`、重复路径、文件与目录冲突、链接、设备、FIFO、稀疏文件和 setuid/setgid 权限。目录由文件路径创建，归档无需目录条目。限制为最多 4096 个资源文件、1 MiB 元数据、512 MiB 展开数据；HTTPS 归档下载上限为 128 MiB。这些是资源边界，不是固定文件清单。

## 安装、升级和回滚

所有清单资源安装到 `/usr/local/libexec/xdrive/`。用户数据、账号配置、Nginx/Caddy 和 systemd 配置位于这个目录之外；系统集成的变更由对应版本的安装或升级脚本显式执行，发布清单不能向任意系统路径写文件。

安装器先核对归档 SHA-256，再在私有暂存目录提取唯一的启动二进制，使用它的 `release-package prepare` 命令验证完整归档。所有文件通过大小、权限、哈希和路径校验后，才展开资源并安装。

升级器验证当前安装的清单和文件，预先展开新版本到同一文件系统中的暂存目录，持久化这些文件，然后进入维护状态、停止 XDrive、创建回滚 hold 和数据库快照。迁移和 doctor 成功后切换整个应用目录，最后启动服务并执行 readyz 检查。

新清单没有列出的旧资源随旧应用目录一起移出，避免留下过期资源。安装目录中出现管理员自行添加或改动的文件时，升级会在停止服务前拒绝，而不会覆盖或丢弃这些文件。配置和业务数据不属于这个检查范围。

就绪检查失败时恢复原应用目录和数据库快照，包含原有资源、安装清单、二进制和辅助脚本。升级备份同时保存完整的 `application.old/`、数据库快照及供旧运维步骤使用的单独二进制/辅助脚本副本。进程中断后保留 hold、维护状态和可恢复目录，后续升级拒绝继续覆盖；不能仅删除 hold 后盲目重试。

卸载按照已安装清单删除资源，只删除空的资源目录，保留未登记的管理员文件、业务数据和备份。

## 旧版更新器的兼容路径

v1.3.4 和 v1.3.6 的已经部署的代码只接受五个固定成员，无法通过修改 GitHub 上的新代码使这些旧程序立即理解任意文件归档。

因此每个稳定版发布两套不同用途的包：

| 归档名 | 内容和使用者 |
| --- | --- |
| `xdrive-vVERSION-linux-ARCH-package.tar.gz` | 目标版本的完整清单及全部资源；供新安装、手动升级和新网页更新器使用 |
| `xdrive-vVERSION-linux-ARCH.tar.gz` | 旧更新器兼容入口；首次 v1.3.7 为同版本五成员包，以后携带固定、不可变的 v1.3.7 过渡程序 |

过渡包的归档名遵循旧更新器固定下载路径，内部 `version` 明确是 v1.3.7；不能将其当作目标版本的完整安装包。v1.3.7 发布时同时生成这两类包；未来的打包器下载并校验已发布 v1.3.7 的过渡包，核对内部版本、架构和文件清单后复制到兼容入口。不得从未来版本重新构建或静默更改该过渡包。离线打包可用 `--bridge-dir DIRECTORY` 提供包含原始过渡包和 `SHA256SUMS` 的目录。

旧 VPS 更新到过渡版后，新服务只继续最近 15 分钟内用户已经确认的同一目标版本与同一请求编号。它等待旧 root 更新任务成功并解除回滚 hold，再排队完整包更新。新 root 更新器再次核对 GitHub 最新版与已确认的版本是否一致；版本发生变化会停止，不会擅自改成其他版本。此机制仅适用于固定过渡版启动时的原请求，不是后台自动升级或定时更新。

新版更新器优先选择 `-package.tar.gz`；从 v1.3.7 起缺少完整包时拒绝安装，不把过渡包当作已完成的目标版本。更早的发行版保留旧包格式读取路径；升级版本必须高于已安装版本，网页更新还绑定用户确认的具体目标版本。

v1.3.5 部署过不同的七成员校验器。一个归档无法同时满足旧代码的“必须五个”和“必须七个”，因此这一个版本仍需用新完整包里的 `upgrade.sh` 手动升级一次；随后所有新增文件都由清单协议处理。不能复写已发布的 v1.3.5 或 v1.3.6 归档来伪装消除该限制。

## 发布门禁

发布上传两种架构的完整包、两个兼容入口及包含全部四个摘要的 `SHA256SUMS`。v1.3.7 是首个过渡版，必须先完成发布；后续版本打包找不到或校验不过该不可变包时拒绝发布。

验收覆盖多文件安装、旧资源移除、全部应用文件回滚、清单损坏、路径/类型拒绝、旧版过渡授权范围和完整包选择。移交正式版前还应在 Linux systemd 环境演练两阶段旧版本升级及中断恢复；本机隔离脚本测试不替代该演练。
